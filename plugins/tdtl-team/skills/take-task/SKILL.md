# Провести задачу до слияния

Работаешь в репозитории продукта. Правила репозитория (`CLAUDE.md`, `.claude/`) главнее этого навыка: там проверки, стоп-список и демо именно этого репозитория. Слияние после проверок делает исполнитель сам. Правки проверок сливаются по вердикту проверяющего линии; секреты и рабочие базы — только по «да» из колонки «Секреты и боевая база» таблицы линий (D-0088).

**Роли (D-0088).** Тот, кто ведёт задачу по этому навыку, — **конвейер**: запуск по расписанию, человек в Claude Code или агент в чате. Спека, тесты, код, ревьюер и PR — его шаги, в журнале он пишет от имени конвейера своей линии («Конвейер» или «Паровоз»). **Архонт** написал зерно, **техлид линии** (Дедал или Хугин) — техпроект и раздел «Для разработки». **Проверяющий линии** (Астерион или Мунин) проверил зерно до тебя и проверяет после: правки проверок, сверку после слияния, приёмку блока (навык `asterion`). Ниже имена — линии TradeLab; в ТД+XP читай их по таблице линий.

**Задачи строго подряд.** Закончил или припарковал одну — потом следующая; две задачи одновременно одна сессия не ведёт. Память между сессиями — журнал задачи: после каждого шага запись «что сделано, что дальше», чтобы следующая сессия продолжила с этого места, а не с начала.

## Линии
Две линии разработки. Таблица — одна, здесь; остальные навыки ссылаются на неё.

| Линия | Проекты | Репозитории | Техлид / конвейер / проверяющий | Владелец линии | «Да» на волну | Секреты и боевая база | Аккаунт GitHub | Уведомления проверяющего |
|---|---|---|---|---|---|---|---|---|
| TradeLab | все проекты без своего конвейера (T-0349) | все репозитории TDTL-projects, кроме репозиториев других линий и вне линий (сейчас это tradelab-app, tl-pm-demo, team-plugin) | Дедал / Конвейер / Астерион | Ерлан | Ерлан | Ерлан | Ерлана | push Ерлану (`PushNotification`) |
| ТД+XP | P-08 | DocsSystem | Хугин / Паровоз / Мунин | Наиль | Наиль | Наиль | Наиля | сообщение Наилю (`send_message`, без `weekend`) |

**Вне линий: module_dt_check (SP-24), владелец Наиль — задачи с этим репозиторием в «К разработке» не ставят и ни один конвейер их не ведёт, PR не берёт ни один проверяющий; слияние и выкладка — по команде владельца.**

Владелец линии — тот, кому вопросы Q-… и задачи «Ответить на Q-…», принимающий задач «Приёмка», кому шаги приёмки глазами, сводка волны и «что ждёт». «Ерлан» в правилах этого навыка и навыков `asterion`, `dedal`, `wave`, `pm` — владелец линии из таблицы.

**Какая у тебя линия.** Запуск по расписанию — по инструкции запуска («кто ты»): Конвейер и Астерион — TradeLab, Паровоз и Мунин — ТД+XP. В разговоре — по проекту задачи: P-08 (с подпроектами) — ТД+XP, остальные — TradeLab; PR без задачи — по репозиторию из таблицы; нет ни задачи, ни PR — по имени, к которому обратились («Хугин, …», «Паровоз, …», «Мунин, …» — ТД+XP). Задача или PR чужой линии — не твои. Разделять очередь `take_next_for_dev` между линиями — дело трекера (T-0349): трекер всё же выдал задачу чужой линии — не начинай, «Остановка» с вопросом владельцу своей линии «трекер выдал задачу линии <линия>».

## Метки в журнале
По этим фразам запуски и Астерион понимают друг друга. Пиши их дословно, с начала записи; других слов для того же не придумывай.

Метки одни для обеих линий; имя в начале — своей линии: в ТД+XP Конвейер → Паровоз, Астерион → Мунин, Дедал → Хугин, остальные слова те же: «Паровоз: запуск начат», «Мунин: проверка не ослаблена — PR #N».

| Метка | Кто пишет | Что значит |
|---|---|---|
| «Конвейер: запуск начат» | исполнитель — первой записью каждой сессии, которая берёт, продолжает или возвращает задачу | задачу ведут: зерно, статус, ветку и PR не трогать |
| «Конвейер: запуск закончен: …» | исполнитель, когда закончил работу над задачей в этой сессии | можно смотреть |
| «Конвейер: правка проверок вне зерна — …» | исполнитель, на остановке после п.3 | тест прежней задачи меняется, а в зерне этого нет — решает Астерион (раздел 1 навыка `asterion`), не владелец линии |
| «Ревьюер: …» | исполнитель, после последнего круга ревью | что нашли, что исправлено, что отложено и почему |
| «Астерион: проверка не ослаблена — PR #N» | Астерион, журнал задачи и PR | правки проверок можно сливать |
| «Астерион: проверка ослаблена — PR #N: …» | Астерион, журнал задачи и PR | исправляй в той же ветке |
| «Астерион: нужны правки в PR #N — …» | Астерион, журнал задачи и PR | исправляй в той же ветке |
| «Астерион: доделка — …» | Астерион, комментарий задачи | задача вернулась в «В работе» после слияния или приёмки |
| «да» | владелец из колонки «Секреты и боевая база»: в TradeLab Ерлан — комментарий в задаче трекера от участника «Ерлан» или его слова в разговоре, который ведёт задачу; в ТД+XP Наиль — комментарий в задаче трекера от участника «Наиль» или его слова в разговоре, который ведёт задачу | слияние секретов или рабочей базы разрешено |

- Задачу ведут, пока последняя запись «Конвейер: запуск начат» новее последней «Конвейер: запуск закончен» (в ТД+XP — «Паровоз: …»). Поэтому в тексте записи о начале слов «запуск закончен» не пиши.
- Записи «Дедал: нужны правки…» и «Дедал: доделка…» (до 18.11.2026) читай как записи Астериона.
- Вердикты засчитываются по автору записи в журнале — проверяющему своей линии. TradeLab: участник «Астерион» (до переименования — «Дедал (CTO)»), как раньше; запись Ерлана — не вердикт. ТД+XP: участник «Мунин» и владелец линии — участник «Наиль»; запись Наиля с той же меткой засчитывается, даже если начинается с «Астерион:» (он проверял в своём чате). Записи участников другой линии не засчитываются: по задаче P-08 запись участника «Астерион» — не вердикт, по задаче вне P-08 запись участника «Мунин» — тоже. Те же слова от другого участника — не вердикт. Комментарии в PR на GitHub за «да» и за вердикт не считаются: туда пишут с одного аккаунта GitHub линии, в том числе агенты.
- Сторож трекера прячет записи с длинными номерами (семь цифр подряд и больше: номер запуска CI, полный хеш коммита) — вместо них видно «запись на проверке», и метка пропадает. Такие номера — только в ссылки. Трекер ответил «проверь» — напиши метку заново, без номера.

## 1. Взять
- **Репозиторий вне линий — первым, до проверки вердикта.** Трекер выдал задачу, у которой строка «Репозиторий» — из строки «Вне линий» таблицы линий (или задача входит в SP-24), — не начинай: вердикта у такого зерна не будет никогда, «Остановку» не оформляй и запись «запуск начат» не пиши. Верни её владельцу двумя правками `update_task`: сначала статус «Предложена»; потом снова `get_task` (первая правка подняла версию) и отдельной правкой ответственный — владелец, Наиль, причина «репозиторий вне линий — ведёт владелец» (передача по правилу трекера идёт без других полей). Журнал: «Конвейер: запуск закончен: репозиторий вне линий — вернул владельцу» (в ТД+XP — «Паровоз: …»). Бери следующую. Конкретную задачу с таким репозиторием (`take_for_dev T-…`) не бери — скажи человеку.
- **Зерно проверено?** (D-0088 п.3). В журнале задачи (`get_task`) последняя запись проверяющего линии по зерну — «Астерион: готово к разработке (версия N)» (в ТД+XP — «Мунин: …»), и после неё нет «к разработке не готово». Прежняя запись «Дедал: готово к разработке» (до 18.11.2026) не считается: те зёрна проверялись по старому порядку, Астерион проверит их заново. Зерно после вердикта не правят; видишь по журналу или комментариям, что правили, — считай, что вердикта нет.
- Конкретную задачу сначала открой (`get_task`): вердикта нет — не бери, скажи человеку: «зерно не проверено, нужен Астерион» (в ТД+XP — Мунин). Есть — `take_for_dev T-…`.
- Следующую по очереди: `take_next_for_dev` с направлением из инструкции запуска (TL — TradeLab, ORG — трекер, плагин и P-08; задачи между линиями делит трекер). Очередь, зависимости и «задачи с базой по одной» решает трекер — не обходи их. Трекер выдал задачу без вердикта — не начинай: «Остановка» с причиной «вердикт Астериона по зерну» (в ТД+XP — «вердикт Мунина по зерну»), бери следующую.
- Не взялось — скажи почему (ответ трекера) и закончи.
- Сразу запись в журнал (`add_worklog`): «Конвейер: запуск начат. Идёт разработка: до записи о конце запуска не меняйте зерно, статус, зависимости и вопросы этой задачи, ветку claude/T-xxxx-… и её PR». Ведёшь не по расписанию — допиши в скобках, кто: «(вручную: Claude Code у Наиля)», «(вручную: чат Ерлана)». В ссылках — эта сессия, если её адрес известен. Без этой записи проверяющий примет твой PR за чужой и может слить его посреди правок.
- Продолжаешь задачу — новая сессия, возврат из «Ожидания», правки по замечанию Астериона, доделка — начни с такой же записи и иди с шага, на котором остановились (по журналу), а не с `take_for_dev`.
- Репозиторий задачи — строка «Репозиторий» в разделе зерна «Для разработки (Дедал)» или «Для разработки (Хугин)» (ТД+XP); строка «Меняет базу» — там же. Открыт не он — подключи нужный (`add_repo`, клон). Нет доступа — «Остановка», не обходи.

## 2. Ветка, зерно, факты
- От свежего `main`: `claude/T-xxxx-коротко`. Номер задачи в имени ветки и в названии PR обязателен — по нему трекер двигает статус.
- Зерно — в `specs/T-xxxx/seed.md` как есть.
- **Техпроект.** В зерне строка «Техпроект: docs/waves/…» — этот файл в `main` и есть общий план волны: какие таблицы заводит твоя задача, а какие — соседние, кто что видит, какие файлы общие. Файла в `main` нет — «Остановка» с причиной «слить техпроект: <файл>».
- **Факты.** У шага «спека и тесты» нет доступа к трекеру и базе. Зерно опирается на то, чего нет в коде (что отвечает инструмент трекера, сколько записей такого вида в базе, как выглядит запись), — выгрузи это в `specs/T-xxxx/data.md`: коротко, без данных клиентов и личных почт. Зерну хватает кода — файл не нужен. Замечания Астериона «к сведению» из записи «готово к разработке» в журнале задачи — туда же, списком: шаг «спека и тесты» учтёт их в спеке.
- **Доделка.** Задача вернулась в «В работе» с комментарием «Астерион: доделка — …» или её вернул человек (по ней уже был слитый PR) — прочитай комментарии в `get_task`: работа — то, что в них просят, в рамках зерна. Ветка новая: `claude/T-xxxx-доделка`. Прежний замок `specs/T-xxxx/tests.lock` и файлы из него не трогаешь: новые тесты — в новых файлах, их пути — в новом замке `specs/T-xxxx/tests-2.lock` (следующая доделка — `tests-3.lock`).

## 3. Спека и тесты до кода
Запусти агента `spec-tests`. Он пишет спеку (или «идём по зерну»), приёмочные тесты и замок `specs/T-xxxx/tests.lock` (в доделке — следующий по номеру замок).
- Ответил `СТОП` → раздел «Остановка».
- Ответил `НУЖНЫ ДАННЫЕ: …` → дополни `specs/T-xxxx/data.md` тем, что он назвал, и запусти его снова. Взять неоткуда — «Остановка».
- Ответил `ПРАВКА ПРОВЕРОК ВНЕ ЗЕРНА: …` → новое поведение по зерну делает неверной строку теста прежней задачи, а строка зерна «Правки проверок» её не называет. Тест не правишь. Коммит «T-xxxx Спека и тесты» и push ветки, затем «Остановка» с причиной «вердикт Астериона по зерну» (в ТД+XP — «вердикт Мунина по зерну»); вопрос владельцу линии не заводишь. Журнал: «Конвейер: правка проверок вне зерна — файл и тест; почему краснеет (пункт зерна); где в спеке; ссылка на ветку» (в ТД+XP — «Паровоз: …»).
- Иначе — коммит «T-xxxx Спека и тесты» и push ветки. PR пока не открывай: CI запускается на PR, а тесты ещё красные.
- Журнал: «Конвейер: спека и тесты — что затрагивает, меняет ли базу, какие тесты, какие проверки прежних задач меняются».

## 4. Код
- Пиши, пока тесты под замком не станут зелёными. **Файлы из замков своей задачи не правь** — хук не даст, а где хука нет, сверит ревьюер. Кажется, что тест неверен или задача невыполнима — не обходи: «Остановка».
- **Противоречивый тест своей задачи** — единственное исключение. Тест под замком этой задачи сам себе противоречит (части дают 5, а итог ждёт 6; тест сам ставит задачу и ждёт подпись вкладки без числа) или противоречит зерну либо правилу уже слитой задачи, а код делает ровно по зерну. Тогда вопрос владельцу линии не заводишь:
  1. Правишь только противоречащие строки, так, чтобы тест ловил ту же ошибку, что задумано (не «принимать что угодно»). Ничего не удаляешь и не отключаешь. Пути исправленных файлов — в новый замок `specs/T-xxxx/tests-2.lock` (следующий — `tests-3.lock`).
  2. Ревьюер подтверждает разбор: противоречие есть, код по зерну, правка его не ослабляет. Не подтвердил — «Остановка» с вопросом, как раньше.
  3. Журнал: файл и строка, в чём противоречие, чем доказано, что стало. Дальше п.9: это правка проверок — «Остановка» с причиной «вердикт Астериона по PR #N».
  Не ясно, кто прав — тест или код, правка меняет смысл зерна, или противоречивых строк больше трёх — это не сюда: «Остановка» с вопросом владельцу линии.
- **Тесты прежних задач** (в том числе под их замками) меняешь, только если спека в «Проверках» называет, какой тест и почему: новое поведение по зерну делает старое утверждение неверным. Меняешь ровно названное. Это правка проверок — п.9. Старый тест покраснел, а в спеке про него ничего — не подгоняй его: «Остановка».
- Рамка — спека или зерно, таблицы и общие файлы — по техпроекту. Видишь лучший путь — одна строка в «Развилки», делай как написано.

## 5. Проверки у себя
Всё, что требует репозиторий (навык `verify` или `CLAUDE.md`), включая базу, если её можно поднять. Красное — чини; три попытки не помогли — «Остановка».

**Неустойчивый тест.** Тест упал, а при повторе прошёл без правок — это не «прошло». Один перезапуск можно; дальше — запись в журнал с названием теста, строка «неустойчивый тест: …» в описании PR и задача на починку (нет такой — заведи, навык `new-task`). Второй раз подряд молча не перезапускай.

## 6. Ревьюер
Агент `reviewer` на дифф. Блокирует — чини и запусти ещё раз; после двух кругов блокеры остались — «Остановка».
- Журнал, одной записью после последнего круга: «Ревьюер: блокеры — …; исправлено — …; отложено — … (почему)». Нет находок — «Ревьюер: находок нет». Отложенное без причины не оставляй. По этой записи Астерион после слияния видит, что ты отбросил.
- **Урок.** Ревьюер нашёл блокер, который не поймал ни один тест под замком, — допиши пункт в `specs/LESSONS.md` репозитория: общий случай в одном-двух предложениях, без истории задачи («имена, которые кончаются на «ь»», «две сессии пишут одновременно»). Файла нет — создай. Не больше 30 пунктов: похожие случаи объединяй. Шаг «спека и тесты» читает этот файл перед следующей задачей.

## 7. PR и CI
- Подтяни `main` (`git fetch origin main && git merge origin/main`), снова проверки из п.5, если что-то пришло.
- **После ревьюера код не меняется молча.** Чинил красный CI, разбирал конфликт с `main` или правил что-то ещё после последнего круга ревью — и это не только номер версии и номер миграции, — ревьюер ещё раз на новый дифф (п.6) и новая запись «Ревьюер: …». Иначе правка старого теста ради зелёного CI уйдёт в `main` мимо всех.
- Открой PR в `main`: «T-xxxx Название задачи». **Сразу готовым, не черновиком**: черновик не видят ни трекер, ни Астерион, и задача встанет молча. Среда всё же открыла черновик — сними отметку сразу (`gh api -X POST repos/<владелец>/<репо>/pulls/<N>/ccr/ready_for_review`); не снимается — «Остановка» с причиной «снять черновик с PR #N»: отметку снимет Астерион или Ерлан.
- В описании по-русски: что сделано; демо «открыть → нажать → увидеть»; что проверено и чем; развилки; меняет ли базу; какие проверки прежних задач изменены и почему. Трекер сам поставит «На проверке».
- Дождись CI. Красный — почини в той же ветке; два круга не помогли — «Остановка». В репозитории без CI — проверки из п.5 и есть доказательство, так и напиши в PR.
- Правишь уже открытый PR — поставь первой строкой его описания «НЕ СЛИВАТЬ: идут правки» и убери, когда закончил.

## 8. Демо
По навыку репозитория `demo` или его `CLAUDE.md`. Пройди на preview то, что открывается без человека; непроверенное в демо не пиши. Экран за входом, куда код приходит человеку, ты на preview не откроешь — его доказывает твой приёмочный тест интерфейса в CI, а сценарий целиком пройдёт Астерион на приёмке блока. Демо из-за этого не остановка: так и напиши в PR — что проверено тестом, что увидит приёмка.

## 9. Правки проверок и стоп-список
Перед слиянием, после последнего подтягивания `main`, запусти `scripts/stop-list.sh` репозитория и сверься с его `CLAUDE.md` (как читать вывод скрипта — там же). Скрипт видит не всё: сам пройди по списку изменённых файлов (`git diff --stat origin/main...HEAD`) и сверь его с пп. 2 и 3 ниже и с замками прежних задач (`specs/*/tests*.lock`, кроме своих).

1. **Чисто** — скрипт ничего не назвал, и в диффе нет ничего из пп. 2 и 3. Сливаешь сам (п.10).
2. **Правки проверок**: CI, хуки, сторожа, тесты базы, тесты прежних задач и чужие замки, настройки тестов, настройки Claude (`.claude/`, `.mcp.json`), скрипты проверок — и то, что назвал ревьюер. «Остановка» с причиной «вердикт Астериона по PR #N» (в ТД+XP — «вердикт Мунина по PR #N»). PR при этом открыт, зелёный и не черновик. В журнале простыми словами: какие проверки меняются и почему, где это в спеке. Сам не сливаешь.
3. **Секреты и рабочие базы**: `.env*` и ключи; база, функции, права и вход трекера и то, что их выкатывает; боевая база TradeLab, когда она появится; в DocsSystem рабочие базы и их граница — по `CLAUDE.md` репозитория DocsSystem. «Остановка» с причиной «да Ерлана на слияние» (в ТД+XP — «да Наиля на слияние»); вопрос Q-… не заводи — ответ владельцу линии готовит проверяющий линии.

Есть и 2, и 3 — причина «да Ерлана на слияние» (в ТД+XP — «да Наиля на слияние»), а в журнале допиши: «в PR есть и правки проверок — нужен ещё вердикт Астериона» (в ТД+XP — «… вердикт Мунина»). Такой PR сливается, когда есть и вердикт, и «да».

Вердикт «проверка не ослаблена» относится к тому коммиту, который проверяющий назвал в записи. Менял после него файлы проверок (`git diff <коммит>..HEAD --stat`) — вердикт больше не действует: снова «Остановка» с причиной «вердикт Астериона по PR #N» (в ТД+XP — «вердикт Мунина по PR #N»).

Нет ни скрипта, ни такого раздела в `CLAUDE.md` — считай правками проверок: CI, хуки, настройки Claude, замки и тесты прежних задач, скрипты, которые выполняются у людей или в проверках; рабочей базой — миграции и серверные функции, права и вход. Сомневаешься — считай, что попало.

## 10. Слияние
- Прямо перед слиянием ещё раз подтяни `main` и сверь то, за что спорят PR: номер версии (запись в списке изменений) и номер миграции — следующие после `main`. Разошлись — поправь последним коммитом и дождись CI.
- `gh api -X PUT repos/<владелец>/<репо>/pulls/<N>/merge -f merge_method=squash`. Где есть CI, GitHub сам не сольёт без зелёного.
- Ответ «ветка отстала» — `gh api -X PUT repos/<владелец>/<репо>/pulls/<N>/update-branch`, дождись CI, слей.
- Среда не дала слить — не обходи и не повторяй по кругу: «Остановка» с причиной «слить PR #N: среда не дала», в журнале — что ответила среда.
- Трекер сам поставит «Готово». Репозиторий выкатывает сам при слиянии — проверь, что выкатка прошла (как — в его `CLAUDE.md`).
- Журнал: «Конвейер: запуск закончен: что сделано, ссылка на PR, что проверено тестом, что увидит приёмка».
- После слияния Астерион сверяет сделанное с зерном. Нашёл расхождение — задача вернётся в «В работе» с комментарием «Астерион: доделка».
- PR, которые ведут не по этому навыку (другой разработчик, правка по решению D-…, документ), проверяет и сливает Астерион (навык `asterion`, D-0041).

## Остановка
Не проталкивай через блокер — паркуй задачу и бери следующую.
1. Журнал: что мешает и какой ответ нужен, ссылка на ветку или PR.
2. Задача — в «Ожидание». В «чего ждём» — только одно из двух, иначе остановку никто не найдёт:
   - одна из шести причин своей линии, дословно (по ним тебя находит проверяющий):
     - TradeLab: «вердикт Астериона по зерну», «вердикт Астериона по PR #N», «слить PR #N: среда не дала», «снять черновик с PR #N», «слить техпроект: <файл>», «да Ерлана на слияние»;
     - ТД+XP: «вердикт Мунина по зерну», «вердикт Мунина по PR #N», «слить PR #N: среда не дала», «снять черновик с PR #N», «слить техпроект: <файл>», «да Наиля на слияние»;
   - номер вопроса Q-…. Любая другая остановка (красный CI после двух кругов, блокеры ревьюера, нет доступа к репозиторию, тест кажется неверным — кроме противоречивого теста своей задачи из п.4 и правки проверок вне зерна из п.3, `СТОП` от шага «спека и тесты») — всегда вопрос: `add_note` (вопрос, к задаче) простыми словами и задача «Ответить на Q-…» тому, кто отвечает (обычно владелец линии из таблицы), со сроком через неделю (D-0027).
3. Журнал: «Конвейер: запуск закончен: остановка — …».
4. Вернуться можно, когда причина снята. Сначала верни задачу в «В работе» (`update_task`), потом:
   - вопрос закрыт ответом — продолжай с шага, на котором остановился;
   - остановка была на правке проверок вне зерна (п.3), а последняя запись Астериона по зерну — «готово к разработке (версия N), правка проверок: …» — эта запись теперь часть зерна. Положи её в `specs/T-xxxx/data.md` и иди с п.3 в той же ветке: шаг «спека и тесты» записывает в «Проверки» ровно названную правку, дальше как обычно (п.4 вносит её, п.9 — PR на вердикт Астериона как правка проверок). Другую правку проверок эта запись не разрешает;
   - последняя запись Астериона по зерну — «готово к разработке» — иди с п.2 (ветка, зерно), `take_for_dev` заново не нужен;
   - файл техпроекта появился в `main` — иди с п.2;
   - PR больше не черновик — жди CI и иди с п.8;
   - «Астерион: проверка не ослаблена — PR #N», PR ещё не слит, после названного в записи коммита файлы проверок не менялись, секретов и рабочей базы в PR нет — слей (п.10);
   - «Астерион: проверка ослаблена» или «Астерион: нужны правки» новее твоей последней записи — исправь то, что он написал, в той же ветке и снова пройди пп. 5–9;
   - «да» владельца из колонки «Секреты и боевая база» после записи об остановке (в TradeLab — комментарий в задаче трекера от участника «Ерлан» или его слова в этом разговоре; в ТД+XP — комментарий в задаче трекера от участника «Наиль» или его слова в этом разговоре) — слей; в PR были ещё и правки проверок — только когда есть и вердикт проверяющего линии.
   PR уже слит (проверяющим или владельцем линии) — задача закрыта, ничего не делай.

## Запуск по расписанию
Для запланированной задачи конвейера линии («Конвейер» или «Паровоз»). Ключ трекера, репозитории и порядок направлений — в её инструкции; всё остальное — здесь.

**Один дирижёр.** Очередь ведёт одна сессия: берёт задачу, доводит до слияния или остановки, берёт следующую — пока трекер не ответит, что брать нечего. Запуск по часам нужен как будильник: он подхватывает очередь, если её никто не ведёт.

1. **Кто-то уже ведёт?** `find_tasks`: ответственный — свой конвейер (участник «Конвейер» или «Паровоз»), статусы «В работе» и «На проверке» (PR открыт — трекер сразу ставит «На проверке», а дирижёр ещё ждёт CI). По каждой `get_task`: последняя запись «<конвейер>: запуск начат» новее последней «запуск закончен», в ней нет «(вручную: …)», и самой свежей записи «<конвейер>: …» меньше 90 минут — очередь ведёт другой запуск. Закончи одной строкой, ничего не бери.
2. **Выбор задачи**, по порядку:
   - Свои «В работе», потом «На проверке» (PR открыт, но не слит): по п.1 их сейчас никто не ведёт — запуск оборвался или задачу вернули на доделку. В последней записи о начале стоит «(вручную: …)» — задачу ведёт человек или чат, не бери её, сколько бы времени ни прошло. Иначе продолжай с места, где остановились (ветка, PR, журнал, спека). Есть комментарий «Астерион: доделка» (в ТД+XP — «Мунин: доделка») новее последнего слитого PR — это доделка (п.2).
   - Свои в «Ожидании»: причина снята (п.4 «Остановки») — верни в «В работе» (`update_task`) и продолжай.
   - Иначе — `take_next_for_dev` по направлениям из инструкции запуска, в её порядке. Брать нечего — закончи одной строкой с причиной из ответа трекера.
3. **Задача за задачей.** Новая задача — с п.1 этого навыка и по порядку; продолжаемая — запись о начале и с шага, на котором остановились. Слил или припарковал — запись «запуск закончен» и снова п.2. Одновременно две задачи не ведёшь, даже если трекер готов выдать вторую.
4. «К разработке» и «Готово» задачам не ставишь: это админ и трекер.

Не пишем в трекер данные клиентов: номера ДТ, договоров, счетов, суммы, чужие почты.
