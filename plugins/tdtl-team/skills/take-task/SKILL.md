# Провести задачу до слияния

Работаешь в репозитории продукта. Правила репозитория (`CLAUDE.md`, `.claude/`) главнее этого навыка: там проверки, стоп-список и демо именно этого репозитория. Слияние после проверок делает исполнитель сам. Правки проверок сливаются по вердикту Астериона; секреты и рабочие базы — только по «да» Ерлана (D-0088).

**Роли (D-0088).** Тот, кто ведёт задачу по этому навыку, — **конвейер**: запуск по расписанию, человек в Claude Code или агент в чате. Спека, тесты, код, ревьюер и PR — его шаги, в журнале он пишет от имени «Конвейер». **Архонт** написал зерно, **Дедал** — техпроект и раздел «Для разработки». **Астерион** проверил зерно до тебя и проверяет после: правки проверок, сверку после слияния, приёмку блока (навык `asterion`).

**Задачи строго подряд.** Закончил или припарковал одну — потом следующая; две задачи одновременно одна сессия не ведёт. Память между сессиями — журнал задачи: после каждого шага запись «что сделано, что дальше», чтобы следующая сессия продолжила с этого места, а не с начала.

## Метки в журнале
По этим фразам запуски и Астерион понимают друг друга. Пиши их дословно, с начала записи; других слов для того же не придумывай.

| Метка | Кто пишет | Что значит |
|---|---|---|
| «Конвейер: запуск начат» | исполнитель — первой записью каждой сессии, которая берёт, продолжает или возвращает задачу | задачу ведут: зерно, статус, ветку и PR не трогать |
| «Конвейер: запуск закончен: …» | исполнитель, когда закончил работу над задачей в этой сессии | можно смотреть |
| «Ревьюер: …» | исполнитель, после последнего круга ревью | что нашли, что исправлено, что отложено и почему |
| «Астерион: проверка не ослаблена — PR #N» | Астерион, журнал задачи и PR | правки проверок можно сливать |
| «Астерион: проверка ослаблена — PR #N: …» | Астерион, журнал задачи и PR | исправляй в той же ветке |
| «Астерион: нужны правки в PR #N — …» | Астерион, журнал задачи и PR | исправляй в той же ветке |
| «Астерион: доделка — …» | Астерион, комментарий задачи | задача вернулась в «В работе» после слияния или приёмки |
| «да» | Ерлан, комментарий задачи или PR | слияние секретов или рабочей базы разрешено |

- Задачу ведут, пока последняя запись «Конвейер: запуск начат» новее последней «Конвейер: запуск закончен». Поэтому в тексте записи о начале слов «запуск закончен» не пиши.
- Записи «Дедал: нужны правки…» и «Дедал: доделка…» (до 18.11.2026) читай как записи Астериона.
- Сторож трекера прячет записи с длинными номерами (семь цифр подряд и больше: номер запуска CI, полный хеш коммита) — вместо них видно «запись на проверке», и метка пропадает. Такие номера — только в ссылки. Трекер ответил «проверь» — напиши метку заново, без номера.

## 1. Взять
- Конкретную: `take_for_dev T-…`. Следующую по очереди: `take_next_for_dev` с направлением (TL — TradeLab, ORG — трекер и плагин). Очередь, зависимости и «задачи с базой по одной» решает трекер — не обходи их.
- Не взялось — скажи почему (ответ трекера) и закончи.
- В журнале задачи нет записи «Астерион: готово к разработке» (или прежней «Дедал: готово к разработке») — зерно не проверено (D-0088 п.3). Не начинай: «Остановка» с причиной «вердикт Астериона по зерну», бери следующую.
- Сразу запись в журнал (`add_worklog`): «Конвейер: запуск начат. Идёт разработка: до записи о конце запуска не меняйте зерно, статус, зависимости и вопросы этой задачи, ветку claude/T-xxxx-… и её PR». Ведёшь не по расписанию — допиши в скобках, кто: «(вручную: Claude Code у Наиля)», «(вручную: чат Ерлана)». В ссылках — эта сессия, если её адрес известен. Без этой записи Астерион примет твой PR за чужой и может слить его посреди правок.
- Продолжаешь задачу — новая сессия, возврат из «Ожидания», правки по замечанию Астериона, доделка — начни с такой же записи и иди с шага, на котором остановились (по журналу), а не с `take_for_dev`.
- Репозиторий задачи — строка «Репозиторий» в разделе зерна «Для разработки (Дедал)». Открыт не он — подключи нужный (`add_repo`, клон). Нет доступа — «Остановка», не обходи.

## 2. Ветка, зерно, факты
- От свежего `main`: `claude/T-xxxx-коротко`. Номер задачи в имени ветки и в названии PR обязателен — по нему трекер двигает статус.
- Зерно — в `specs/T-xxxx/seed.md` как есть.
- **Техпроект.** В зерне строка «Техпроект: docs/waves/…» — этот файл в `main` и есть общий план волны: какие таблицы заводит твоя задача, а какие — соседние, кто что видит, какие файлы общие. Файла в `main` нет — «Остановка»: техпроект не слит.
- **Факты.** У шага «спека и тесты» нет доступа к трекеру и базе. Зерно опирается на то, чего нет в коде (что отвечает инструмент трекера, сколько записей такого вида в базе, как выглядит запись), — выгрузи это в `specs/T-xxxx/data.md`: коротко, без данных клиентов и личных почт. Зерну хватает кода — файл не нужен.
- **Доделка.** Задача вернулась в «В работе» с комментарием «Астерион: доделка — …» или её вернул человек (по ней уже был слитый PR) — прочитай комментарии в `get_task`: работа — то, что в них просят, в рамках зерна. Ветка новая: `claude/T-xxxx-доделка`. Прежний замок `specs/T-xxxx/tests.lock` и файлы из него не трогаешь: новые тесты — в новых файлах, их пути — в новом замке `specs/T-xxxx/tests-2.lock` (следующая доделка — `tests-3.lock`).

## 3. Спека и тесты до кода
Запусти агента `spec-tests`. Он пишет спеку (или «идём по зерну»), приёмочные тесты и замок `specs/T-xxxx/tests.lock` (в доделке — следующий по номеру замок).
- Ответил `СТОП` → раздел «Остановка».
- Ответил `НУЖНЫ ДАННЫЕ: …` → дополни `specs/T-xxxx/data.md` тем, что он назвал, и запусти его снова. Взять неоткуда — «Остановка».
- Иначе — коммит «T-xxxx Спека и тесты» и push ветки. PR пока не открывай: CI запускается на PR, а тесты ещё красные.
- Журнал: «Конвейер: спека и тесты — что затрагивает, меняет ли базу, какие тесты, какие проверки прежних задач меняются».

## 4. Код
- Пиши, пока тесты под замком не станут зелёными. **Файлы из замков своей задачи не правь** — хук не даст, а где хука нет, сверит ревьюер. Кажется, что тест неверен или задача невыполнима — не обходи: «Остановка».
- **Тесты прежних задач** (в том числе под их замками) меняешь, только если спека в «Проверках» называет, какой тест и почему: новое поведение по зерну делает старое утверждение неверным. Меняешь ровно названное. Это правка проверок — п.9. Старый тест покраснел, а в спеке про него ничего — не подгоняй его: «Остановка».
- Рамка — спека или зерно, таблицы и общие файлы — по техпроекту. Видишь лучший путь — одна строка в «Развилки», делай как написано.

## 5. Проверки у себя
Всё, что требует репозиторий (навык `verify` или `CLAUDE.md`), включая базу, если её можно поднять. Красное — чини; три попытки не помогли — «Остановка».

**Неустойчивый тест.** Тест упал, а при повторе прошёл без правок — это не «прошло». Один перезапуск можно; дальше — запись в журнал с названием теста, строка «неустойчивый тест: …» в описании PR и задача на починку (нет такой — заведи, навык `new-task`). Второй раз подряд молча не перезапускай.

## 6. Ревьюер
Агент `reviewer` на дифф. Блокирует — чини и запусти ещё раз; после двух кругов блокеры остались — «Остановка».
- Журнал, одной записью после последнего круга: «Ревьюер: блокеры — …; исправлено — …; отложено — … (почему)». Нет находок — «Ревьюер: находок нет». Отложенное без причины не оставляй. По этой записи Астерион после слияния видит, что ты отбросил.
- **Урок.** Ревьюер нашёл блокер, который не поймал ни один тест под замком, — допиши пункт в `specs/LESSONS.md` репозитория: общий случай в одном-двух предложениях, без истории задачи («имена, которые кончаются на «ь»», «две сессии пишут одновременно»). Файла нет — создай. Не больше 30 пунктов: похожие случаи объединяй. Шаг «спека и тесты» читает этот файл перед следующей задачей.

## 7. PR и CI
- Подтяни `main` (`git fetch origin main && git merge origin/main`), снова проверки из п.5, если что-то пришло.
- Открой PR в `main`: «T-xxxx Название задачи». **Сразу готовым, не черновиком**: черновик не видят ни трекер, ни Астерион, и задача встанет молча. Среда всё же открыла черновик — сними отметку сразу (`gh api -X POST repos/<владелец>/<репо>/pulls/<N>/ccr/ready_for_review`); не снимается — «Остановка» с причиной «снять черновик с PR #N».
- В описании по-русски: что сделано; демо «открыть → нажать → увидеть»; что проверено и чем; развилки; меняет ли базу; какие проверки прежних задач изменены и почему. Трекер сам поставит «На проверке».
- Дождись CI. Красный — почини в той же ветке; два круга не помогли — «Остановка». В репозитории без CI — проверки из п.5 и есть доказательство, так и напиши в PR.
- Правишь уже открытый PR — поставь первой строкой его описания «НЕ СЛИВАТЬ: идут правки» и убери, когда закончил.

## 8. Демо
По навыку репозитория `demo` или его `CLAUDE.md`. Пройди на preview то, что открывается без человека; непроверенное в демо не пиши. Экран за входом, куда код приходит человеку, ты на preview не откроешь — его доказывает твой приёмочный тест интерфейса в CI, а сценарий целиком пройдёт Астерион на приёмке блока. Демо из-за этого не остановка: так и напиши в PR — что проверено тестом, что увидит приёмка.

## 9. Правки проверок и стоп-список
Перед слиянием, после последнего подтягивания `main`, запусти `scripts/stop-list.sh` репозитория и сверься с его `CLAUDE.md` (как читать вывод скрипта — там же). Три исхода:

1. **Чисто** — сливаешь сам (п.10).
2. **Правки проверок**: CI, хуки, сторожа, тесты базы, тесты прежних задач и чужие замки, настройки Claude (`.claude/`, `.mcp.json`), скрипты проверок — и то, что по пути скрипт не видит, но назвал ревьюер. «Остановка» с причиной «вердикт Астериона по PR #N». PR при этом открыт, зелёный и не черновик. В журнале простыми словами: какие проверки меняются и почему, где это в спеке. Сам не сливаешь.
3. **Секреты и рабочие базы**: `.env*` и ключи; база, функции, права и вход трекера; боевая база TradeLab, когда она появится. «Остановка» с причиной «да Ерлана на слияние»; вопрос Q-… не заводи — ответ Ерлану готовит Астерион.

Нет ни скрипта, ни такого раздела в `CLAUDE.md` — считай правками проверок: CI, хуки, настройки Claude, замки и тесты прежних задач, скрипты, которые выполняются у людей или в проверках; рабочей базой — миграции и серверные функции, права и вход. Сомневаешься — считай, что попало.

## 10. Слияние
- Прямо перед слиянием ещё раз подтяни `main` и сверь то, за что спорят PR: номер версии (запись в списке изменений) и номер миграции — следующие после `main`. Разошлись — поправь последним коммитом и дождись CI.
- `gh api -X PUT repos/<владелец>/<репо>/pulls/<N>/merge -f merge_method=squash`. Где есть CI, GitHub сам не сольёт без зелёного.
- Ответ «ветка отстала» — `gh api -X PUT repos/<владелец>/<репо>/pulls/<N>/update-branch`, дождись CI, слей.
- Среда не дала слить — не обходи и не повторяй по кругу: «Остановка» с причиной «слить PR #N: среда не дала», в журнале — что ответила среда.
- Трекер сам поставит «Готово». Репозиторий выкатывает сам при слиянии — проверь, что выкатка прошла (как — в его `CLAUDE.md`).
- Журнал: «Конвейер: запуск закончен: что сделано, ссылка на PR, что проверено тестом, что увидит приёмка».
- После слияния Астерион сверяет сделанное с зерном. Нашёл расхождение — задача вернётся в «В работе» с комментарием «Астерион: доделка».
- PR, которые ведут не по этому навыку (другой разработчик, правка по решению D-…, документ), проверяет и сливает Астерион (навык `asterion`, D-0041).

## Остановка
Не проталкивай через блокер — паркуй задачу и бери следующую.
1. Журнал: что мешает и какой ответ нужен, ссылка на ветку или PR.
2. Нужен ответ человека — вопрос `add_note` (вопрос, к задаче) и задача «Ответить на Q-…» тому, кто отвечает (обычно Ерлан), со сроком через неделю (D-0027). Для причин из списка в п.3 вопрос не нужен.
3. Задача — в «Ожидание». В «чего ждём» — номер вопроса или одна из причин, дословно (по ним тебя находит Астерион): «вердикт Астериона по зерну», «вердикт Астериона по PR #N», «слить PR #N: среда не дала», «снять черновик с PR #N», «да Ерлана на слияние».
4. Журнал: «Конвейер: запуск закончен: остановка — …».
5. Вернуться можно, когда причина снята:
   - вопрос закрыт ответом;
   - появилась запись «Астерион: готово к разработке» — начинай задачу с п.1;
   - «Астерион: проверка не ослаблена — PR #N», а PR ещё не слит — слей (п.10);
   - «Астерион: проверка ослаблена» или «Астерион: нужны правки» новее твоей последней записи — исправь то, что он написал, в той же ветке и снова пройди п.5–9;
   - Ерлан написал «да» в комментарии задачи или PR после записи об остановке — слей.
   PR уже слит (Астерионом или Ерланом) — задача закрыта, ничего не делай.

## Запуск по расписанию
Для запланированной задачи «Конвейер». Ключ трекера, репозитории и порядок направлений — в её инструкции; всё остальное — здесь.

**Один дирижёр.** Очередь ведёт одна сессия: берёт задачу, доводит до слияния или остановки, берёт следующую — пока трекер не ответит, что брать нечего. Запуск по часам нужен как будильник: он подхватывает очередь, если её никто не ведёт.

1. **Кто-то уже ведёт?** `find_tasks`: ответственный «Конвейер», статус «В работе». По каждой `get_task`: последняя запись «Конвейер: запуск начат» новее последней «запуск закончен», в ней нет «(вручную: …)», и самой свежей записи «Конвейер: …» меньше 90 минут — очередь ведёт другой запуск. Закончи одной строкой, ничего не бери.
2. **Выбор задачи**, по порядку:
   - Свои «В работе», потом «На проверке» (PR открыт, но не слит). В последней записи о начале стоит «(вручную: …)» — задачу ведёт человек или чат, не бери её, сколько бы времени ни прошло. Иначе продолжай с места, где остановились (ветка, PR, журнал, спека). Есть комментарий «Астерион: доделка» новее последнего слитого PR — это доделка (п.2).
   - Свои в «Ожидании»: причина снята (п.5 «Остановки») — верни в «В работе» (`update_task`) и продолжай.
   - Иначе — `take_next_for_dev` по направлениям из инструкции запуска, в её порядке. Брать нечего — закончи одной строкой с причиной из ответа трекера.
3. **Задача за задачей.** Новая задача — с п.1 этого навыка и по порядку; продолжаемая — запись о начале и с шага, на котором остановились. Слил или припарковал — запись «запуск закончен» и снова п.2. Одновременно две задачи не ведёшь, даже если трекер готов выдать вторую.
4. «К разработке» и «Готово» задачам не ставишь: это админ и трекер.

Не пишем в трекер данные клиентов: номера ДТ, договоров, счетов, суммы, чужие почты.
