# Сборка версий схемы BPMN

Схема — один файл `.bpmn` на Диске (D-0032). Когда авторы правят свои копии, скрипт сводит их по id элементов: новое (блоки, стрелки, заметки с вопросами и ответами) добавляет сам, изменения и удаления выносит на решение владельцу схемы.

1. **Файлы.** Нужны исходная версия — та, с которой все начинали (обычно файл на Диске до правок), и версии авторов. Скачай всё в рабочую папку задачи. Не знаешь, какая исходная или чья копия, — спроси: без исходной не отличить «добавил» от «удалил».
2. **Запуск** (ставить ничего не нужно, на Windows — `python` вместо `python3`):
   ```
   python3 "<папка навыка>/scripts/bpmn_merge.py" исходная.bpmn копия1.bpmn [копия2.bpmn …] \
       -o "T-xxxx <схема> (собрано ДД.ММ).bpmn" --report "T-xxxx <схема> (собрано ДД.ММ) отчёт.md" --authors "Андрей,Даниил"
   ```
   Авторы — в том же порядке, что копии. `-o` и `--report` — только новые файлы: если они совпадут с исходной или копией, скрипт остановится и ничего не запишет. `T-xxxx` — задача, к которой относится схема: номер в начале названия исходного `.bpmn`; нет его или он другой, чем у задачи, над которой работаете, — спроси.
3. **Отчёт — человеку простыми словами:** что добавилось само (число — из строки «Добавлено: N»); что нужно решить — по каждому пункту: что было, что стало, кто поменял, и твой совет, если правка похожа на случайную (например, стёрта подпись только у одной ветки развилки). Сдвиг всей схемы на холсте и служебные отметки групп скрипт учитывает сам, это не правки.
4. **Решает владелец схемы** (кто — говорит человек; не сказал — спроси). По каждой правке и удалению — его «да» или «нет». Человек передаёт ответ владельца по пунктам — годится. «Принимай всё», «вроде не против» — не ответ: дай человеку список пунктов, чтобы переслать владельцу. Сама ничего не принимаешь и не подставляешь `--accept` без «да» по пункту. Конфликт (два автора по-разному поменяли одно) — сначала решить, чью версию брать.
5. **Принятые** — тот же запуск ещё раз с `--accept id1,id2`. Принимается только то, что названо: положение блока на схеме — отдельная строка отчёта со своим id `…_di`, его называют отдельно. Если у стрелки поменялся конец, принимай и её `…_di`, иначе линия останется нарисованной к старому блоку. Перенос блока в другую дорожку — правка самого блока («дорожка: … → …»); если один автор блок переименовал, а другой перенёс, это конфликт по блоку: после выбора версии вторую правку внесите в собранную руками. id без правки или с опечаткой скрипт назовёт в «Не получилось» — переспроси. Удалять скрипт откажется, если на элемент ещё ссылаются (стрелки, событие на границе, развилка по умолчанию, пул, группа — на своё название), на нём держится чертёж или внутри него есть элементы (подпроцесс, дорожка с блоками), — скажи причину из отчёта. Порядок в `--accept` важен: сначала то, что ссылается или вложено, потом то, на что ссылаются (`группа,её_название`; `блок,подпроцесс`). Если автор впервые завёл дорожки, в собранной появятся пустые дорожки, а размещение блоков по ним придёт правками на решение.
6. **Стоп-сигналы в отчёте** — результат не выкладывать, показать человеку:
   - «Собранный файл не цельный»;
   - «пропала большая часть элементов» — схему перерисовали с новыми id, сборка по id тут не работает. Автору — править исходный файл, не меняя id существующих блоков.
7. **Готово** — только когда владелец ответил по всем пунктам: собранную версию на Диск новым файлом (навык `publish-to-drive`). Промежуточную версию до его ответа не выкладываешь — иначе на Диске будут две «собранные» и кто-то начнёт править не ту. Старые копии не удаляешь; предложи убрать их в «Референс» (навык `tidy-drive`). Дальше все правят только собранную.

## Чтобы сборка работала
- id блоков не меняются от версии к версии: правят существующий файл, а не рисуют схему заново. Агенту, который рисует схемы, — правило «существующим элементам id не менять, новым давать новые».
- Проверка самого скрипта: `python3 "<папка навыка>/scripts/test_bpmn_merge.py"`.
